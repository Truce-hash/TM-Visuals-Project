1  Purpose and presentation overview
TM Visuals admin features
A study and presentation guide for Brandon's admin calendar, whole-day availability manager and existing invoice PDF upload. The guide explains what each relevant file and function does, how data moves through the application, and what to demonstrate.
The central design is a separation of responsibilities: views display the interface, viewmodels manage screen state, models describe data, and services communicate with Supabase. main.dart is only the startup entry point.
A short opening you can use
How to explain it: My assigned features are the admin calendar, date availability management and uploading existing invoice PDFs. I used the team's MVVM structure with Provider, so the screens are separate from state management and database operations. An administrator can inspect bookings, close or reopen an entire date without deleting bookings, and attach a PDF invoice to a booking.

2  Architecture and the flow of data
MVVM means Model View ViewModel. The service layer is an additional boundary for network and Storage work.

A calendar request from start to finish
CalendarScreen creates CalendarViewModel with a CalendarDataSource. The viewmodel calls loadMonth and loadAvailability. CalendarService queries Supabase, then CalendarSlot.fromMap converts database maps into objects. The viewmodel saves those results and notifies its listeners. The view rebuilds and displays the returned state.
User action -> View -> ViewModel -> Service -> Supabase
Supabase result -> Service -> Model objects -> ViewModel -> View
How Provider updates the screen
ChangeNotifier is the base class that lets a viewmodel announce state changes. notifyListeners tells listening widgets that something changed. context.watch<T>() subscribes a widget to that state. context.read<T>() obtains an object without subscribing the caller. Consumer<T> rebuilds a selected part of the UI.
Why services are injectable
CalendarDataSource and InvoiceDataSource define contracts. A viewmodel can receive a real Supabase implementation or a fake implementation for a test. This makes it possible to test state changes and error handling without connecting to the live project.
Why the files are separate
A colour or layout change belongs in a view or shared widget. A database query change belongs in a service. A rule about when saving is allowed belongs in a viewmodel. A field or database mapping change belongs in a model. This separation makes code easier to explain, review and test.
How to explain it: Provider connects the screen to its viewmodel. The service retrieves data, the model gives it a clear structure, and the viewmodel tells the screen when to rebuild.

16  Invoice upload algorithm and failure recovery
Upload the PDF and save its metadata
uploadInvoice(...) -> Future<AddInvoiceModel>
lib/services/add_invoice_service.dart  |  line 104
This service method coordinates Storage and Postgres. They are separate operations, so the error-handling code is responsible for recovering a saved row or cautiously cleaning up a rejected upload. There is no single transaction covering both systems.
Normal success path
1. Validate the actual bytes, trimmed reference and booking ID. Require the administrator ID.
2. Build admin_id/booking_id/invoice_id.pdf. The user's original filename is not used as the storage object name.
3. Call _find(invoiceId). If it already exists, return _matching instead of uploading again.
4. Upload binary data with contentType application/pdf and upsert false.
5. Insert invoice_id, admin_id, booking_id, reference and file_path into invoice. Select the created row and return its model.
A duplicate object during a retry
A prior upload might have succeeded even though the client did not receive its response. Storage can then report that the object already exists. The code permits reuse of that path only if uncertainBefore is true and the error matches a duplicate condition. It still does not overwrite the object. The viewmodel locks the inputs so the same attempt keeps the same PDF and metadata.
Recover before deciding to clean up
On an exception, the service first looks for a committed invoice row. If it finds a matching row, it returns success. If no row is visible, cleanup is allowed only for a PostgrestException with a five-character SQL error code beginning 22, 23 or 42, when this attempt definitely uploaded the object and there was no earlier uncertainty. These classes cover input, constraint and syntax/access rejections.
Transport failures, gateway timeouts, unknown error codes and uncertain earlier attempts retain the PDF. A missing row is not proof that a request behind a gateway timeout has stopped. If the recovery query or cleanup also fails, that secondary error is suppressed and the original error is rethrown.
How to explain it: I never delete the PDF just because the connection failed. I first check whether the invoice was saved. Only a definite first-attempt database rejection allows cleanup, because an uncertain insert might still finish later.

22  Supabase data relationships and security boundaries

Read versus write responsibilities
The calendar service reads slot/booking data. The date manager writes only date_availability. The invoice service writes a Storage object and an invoice row. Admin Auth service reads membership and calls Auth. These are distinct operations; a UI status colour does not itself reserve a slot or change a booking status.
What provides real access control
The admin gate controls which screens are visible. The service checks membership before sensitive actions. Server-side Row Level Security and Storage policies must still enforce permissions for direct API requests. A public key alone does not prove authorization. Client-side checks and obscured passwords are not encryption or database access policies.
Availability enforcement on the server
The Dart code never inserts a new booking reservation. Preventing a different booking module or direct API caller from reserving a closed day depends on the deployed server guards and policies. Earlier project work added those guards, but their live definitions were not re-inspected for this documentation task. The current checkout contains no local SQL migration scripts to verify that deployment from source.
How to explain it: Database rows describe the booking and invoice relationships. Storage holds the PDF. UI gates make the workflow usable, while database and Storage policies must remain the final access-control boundary.

24  Likely questions and concise answers
Why did you use MVVM and Provider
The view displays state, the viewmodel coordinates actions, models describe the data, and services access Supabase. Provider connects the state to the widgets. I can change queries or test state without putting database code into the calendar layout.
Why is a closed booked date grey
CalendarViewModel.status checks the whole-day override before checking reservations. Closure controls whether more sessions may be accepted; existing bookings remain visible for the administrator.
Why do you check both booking and selection status
The booking is the overall request. selection_status belongs to its link with a particular time slot. Either side can release the reservation, so the helper treats an inactive status on either side as inactive.
How do you avoid stale month data
Each load increments a request version. A response may update state only if its version is still current and the viewmodel is alive. This handles requests finishing in a different order from the user's clicks.
Why save a path instead of a permanent public URL
The file is kept in a private bucket. I save its stable path and request a temporary signed URL only when opening it. That separates permanent invoice metadata from temporary access.
Does retry guarantee no duplicate invoices ever
No. It reuses one ID for one unresolved in-memory attempt and checks for a saved row. A separate completed/new attempt can create another invoice. Recovery does not survive the end of the authorized subtree or a full app restart.
Why not delete every failed upload
A timeout can occur while the database insert is still running. Deleting the PDF then could leave a late committed invoice pointing at a missing file. Cleanup is restricted to definite first-attempt SQL rejections.
What did you deliberately leave to other modules
Booking creation and approval, client/profile management, the invoice list/details workflow, portfolio/content management and service management belong to separate team modules. My screens connect to them through routes and shared data relationships.
